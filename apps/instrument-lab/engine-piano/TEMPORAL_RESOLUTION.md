# Higher-rate live piano mechanics

The live piano can explicitly run its existing physical engine at 2x or 4x
its host audio rate. `PianoAudio` owns one `LivePiano` and the shared
`fs_couple::pcm_wav::decimate::Decimator`; it is not a second integrator.
Every string/board/shank/felt step and every Rayleigh microphone sample runs
at the higher clock. Every resulting f64 pressure sample reaches the existing
anti-alias filter before conversion to host-rate Float32 at the fixed Pa scale.
There is no interpolation of finished audio, endpoint-only downsampling,
added EQ, gain normalization, retuned tension or new constitutive law.

## Browser and scheduled playback

After rebuilding the piano WASM with the repository's existing build path,
pass `substeps` inside the existing init `options` to either `worker.js` or
`lane-worker.js`:

```js
options: { substeps: 4, boardCoordinates: 32 }
```

The standalone worker uses the requested host sample rate; the scheduled lane
retains its existing 48 kHz context clock. Events and render lengths stay in
host frames. A queued event acts at the first mechanical substep of its frame.
Board-selection probes, separate benchmarks and copied engines use the same
selected clock. The existing governor may change string mode budgets, but
never silently lowers the selected substep count. Greater mechanical work
may require smaller budgets or cause underruns; real-time speed is not promised.

Direct WASM use (after initialization) is also available:

```js
const piano = PianoEngine.withOversampling(48000, 0, 200, 2400, 10, 4);
piano.noteOn(69, 1.2);                 // post-escapement hammer speed [m/s]
const block = piano.render(128);       // 128 host frames, 512 mechanical steps
const info = JSON.parse(piano.info()); // output and mechanical rates, latency
```

`withBoardOversampling` takes a supplied board byte array in place of the
coordinate count, with the same remaining arguments. Original `new PianoEngine`
and `withBoard` calls retain the original single-rate backend, including its
recoverable note-refusal behavior. Omitted `substeps` or explicit `1` uses that
backend. An old deployed WASM lacking the new constructors refuses a higher-rate
request instead of silently playing at 1x. No prebuilt WASM was regenerated by
this source change; using the new constructors requires that build.

## Native API, clocks and failure

`PianoAudio::new(&description, config, substeps)` interprets `config.sample_rate`
as the output clock. `new_with_gas` retains the original explicit GasState ingress.
Factors are 1, 2 or 4, and the existing mechanical ceiling remains 192 kHz.
Thus 48 kHz output admits 4x, 96 kHz admits 2x and 192 kHz admits only 1x.
The played partial band, including later quality changes, remains at or below
45% of the OUTPUT rate. Raising the mechanical rate does not request wider
physical output bandwidth. Internal source tables follow the original engine's
high-rate preparation and existing table caps.

Source counters and energy books remain mechanical; the adapter separately
counts emitted pressure frames, output peak Pa and output full-scale exceedances.
WASM `stats()` keeps its array layout with acoustic values on the host clock.
`info()` reports both clocks, total numerical latency in output frames and
microphone work per output frame. The physical display snapshot still comes
from the source, not a second downsampled mechanical state.

The original microphone runs at the mechanical rate. Its numerical delay is
divided by the factor, then the shared output decimator adds 0, 40 or 44 host
frames at 1x, 2x or 4x respectively. No latency is trimmed or compensated with
future samples. Clones retain the complete source and filter histories.

An error after source progress in `PianoAudio` permanently prevents continuation:
a missing pressure packet cannot be retried against already advanced mechanics.
The completed output prefix remains and the failed suffix is silent. The native
API returns the error; WASM exposes `lastError()` and `isPoisoned()`. Reading the
diagnostic does not unpoison the adapter. This is intentionally stricter than
the legacy browser backend; restarting a failed higher-rate performance requires
a fresh engine. Pre-step invalid controls do not poison it.

## Scope and verification

This changes temporal resolution, not soundboard spatial resolution or modal
coverage. Unstruck strings remain on the live engine's original static image.
Voice minimum ages and retirement scans remain MECHANICAL-step based, just as
in a directly constructed higher-rate LivePiano; their physical-time cadence
therefore differs across factors. No same-time retirement, complete sympathetic
resonance, felt calibration, soundboard convergence or listening-quality claim
is made by this adapter. Compare explicit rates with matched physical parameters
and inspect the actual engine diagnostics.

```sh
cargo test --manifest-path apps/instrument-lab/engine-piano/Cargo.toml --test audio_rate
node --test apps/instrument-lab/tests/piano-oversampling.test.mjs
```

Six authored Rust tests exercise original 1x bit parity, direct high-rate
source/filter equivalence, gas, pedal events, cloned histories, callback splits,
clock/band admission, partial-failure refusal and output-clock descriptions.
They remain unexecuted here because DSR/RCH/Cargo/rustc are unavailable.
Five Node selection tests pass with a recording mock constructor; these do not
execute WASM or piano physics. All three changed/new JS modules pass syntax checks.
An independent convolution reference of the existing shared FIR passed 15
frequency cases; its 30 kHz rejection before 48 kHz output is approximately
117 dB. That is a filter-only calculation, not a rendered-piano alias metric.
Native/WASM compilation, full piano renders, performance measurements and
listening validation remain required.
